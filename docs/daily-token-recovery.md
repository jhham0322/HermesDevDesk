# Daily token recovery

A failed provider turn with explicit daily token exhaustion schedules the same persistent completion-loop process for **the next daily reset at 09:10 Asia/Seoul (UTC+09:00)**. This is the owner-requested retry time, not proof that every provider resets then. A per-response `finish_reason=length`, context-window limit, generic HTTP 429, weekly limit, payment/billing failure, authentication/permission rejection, cancellation, pending approval or uncertain side effect is not eligible.

The original task ID, engine thread, requirements, completed items and operation receipts remain in the state store. The running application checks due work every 30 seconds. It requires the same connected provider fingerprint/session and a non-archived idle task. Expired OAuth sessions are not refreshed by this feature. If the application/computer is off or disconnected at the deadline, the reservation remains until the application and the original connection are available. This feature does not install a Windows startup service or wake the computer.

Before admission, a unique exclusive claim file is flushed and the claimed checkpoint is saved. A second application instance or a restarted ambiguous admission cannot replay that request. If the application exited after admission without a completion event, manual result reconciliation is required. Completed turn evidence releases the uncertain marker. Repeated confirmed daily exhaustion is deferred to the next day, with at most three automatic attempts per original process. Other errors retain the existing stop/review flow. No completed/uncertain command is retried by the scheduler itself.

The Processes panel shows the scheduled Korean time, attempts and cancellation. Its existing Stop action cancels a waiting reservation, persists the stop and prevents later polls from restarting it. A new task has its own independent policy. The resume action uses the existing authenticated `thread/resume` and completion-loop path; it does not create credentials, change provider, override permission denial or remove approvals.

Verification: `Hermes.Tests.exe --daily-quota-only` exercises provider-error classification, Korean calendar boundaries, the real turn-completion reservation hook, state reload, completed-item preservation, missing-engine hold, claim/budget blockers and Stop cancellation. No real paid model, screen input or provider reset is exercised by this suite. Full real-engine admission and overnight execution remain separate integration checks.

Scheduling accepts a provider `turn/completed` failure or a correlated structured `turn/start` RPC rejection with an explicit daily-token error. The RPC reader retains only redacted code/type/message fields (including those in data), not arbitrary payloads. Generic exceptions and thread/resume rejections are excluded. A first-request rejection with images/files/skills is kept for manual recovery because those inputs have not yet been durably admitted; it is never resumed with missing attachments. Thread restoration is revalidated after its await: Stop/cancellation, a newer thread, model/provider/engine changes, approval and uncertain effects prevent turn admission without clearing the stop.
